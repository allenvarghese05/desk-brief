## 2026-11-20 · T56 Dashboard data layer: one connection, rebuild only on change, incremental cache · implementer (opus-5.5)
- Did:
  - **One connection** (`app/components/data.py`): `build_snapshot` runs on `shared_connection`;
    no private second connection. `open_connection(config, env)` and
    `build_snapshot(config, env, now, exclude_tiers)` keep their signatures
    (`open_connection` still returns a new connection the caller closes, for
    `4_Data_health.py`). `shared_connection` gained an optional `env`.
  - **Rebuild only on change**: the first build is synchronous (concurrent callers wait for that
    one build). After it, a call that finds the last listing check 60 s old (`LISTING_CHECK_SECONDS`)
    starts one background check: `store_listing` (one LIST per cached table plus the
    `clean/_CURRENT` read). It rebuilds only if the listing differs, swaps the new connection in, then
    closes the old one after its running query. No caller waits on a check or a rebuild. A
    failed check keeps the old connection serving and records only the exception type.
    `wait_for_refresh(config)` blocks until no check is running (tests).
  - **`data_version(config)`**: the 16-hex SHA-256 fingerprint of the listing the serving
    connection was built from. `_cached`, `_cached_bars` and `_cached_series` take it as a key
    with `DATA_CACHE_TTL_SECONDS = 900`. `CACHE_TTL_SECONDS` stays 60 because `kit.py`'s
    serving-file caches use it and are not covered by the data version.
  - **Incremental table cache** (`store/table_cache.py`): each entry keeps per-key Arrow tables.
    New keys are downloaded and appended. If any cached key of a `date=…/` partition is gone,
    that partition is evicted and every key it still lists is re-read. A per-table lock gives
    single-flight loads. The result is `combine_chunks()`'d once per listing, which brings DuckDB's
    copy from ~200–250 ms to ~30 ms on the 2,000-file store. `invalidate()`, `load_table` and
    `read_files` keep their signatures (pinned by a test). The assumptions are in the module
    docstring.
  - **Dashboard connection options** (`store/duck.py`): `connect(..., skip_views=,
    listing=, clean_version=)`. A skipped view is empty and typed, with no LIST. `httpfs` and
    the R2 secret are set up only if some `DAILY_TABLES` view is still built. `listing` lets the
    connection be built from exactly the listing that was fingerprinted. The defaults keep the
    pipeline's behaviour. The dashboard skips `scorecard` (Sources reads `scorecard_30d.parquet`).
  - **Synthetic store and benchmark** (`tests/bench/`): `synth_store.py DIR` builds 2,000
    observations files in 14 s and 24 MB: one history file per weekday over 2 years, plus the
    rest as Yahoo-quote polls over the last 30 weekdays, 30 runs and 30 dq files.
    `bench_dashboard.py DIR` times one Home render (`build_snapshot` + SPY bars) cold, warm
    (fake clock +61 s, no change) and after one new file (until a render shows it). It uses only
    functions public on main.
- Benchmark (Apple-silicon Mac, macOS 27.0.1 arm64, Python 3.12.14; synthetic store, 2,000 files;
  medians of 7 repeats, three runs each):
  - before: main `d29faf9`, measured with the same script on `git archive d29faf9` sources:
    - cold 2,652–2,655 ms;
    - warm 842–858 ms;
    - rebuild +1 2,453–2,486 ms.
  - after:
    - cold 1,997–2,035 ms;
    - warm 145–169 ms;

  - Warm is ×5.8 on the typical run (×5.0 on the 169 ms outlier), rebuild +1 is ×5.7, cold is ×1.3.
  - The warm floor is the queries themselves (`BriefModel.from_store` ~110 ms, outside Owns).
    The outlier is the background LIST competing for the GIL (a local `rglob`; on R2 the LIST is
    network wait).
- Went wrong:
  - `git checkout -b` could not write `.git/config` (upstream tracking) in the sandbox. The
    branch was created and checked out without tracking. The sandbox hides `.env.example`, so
    git shows it as deleted; only explicit paths were staged.
  - The first bench draft checked the new row right after one render. With the background
    check, that render is served stale by design, so the bench now times until a render shows
    the row. That is one render on main, so the before numbers were re-measured with the final
    script.
- Decisions:
  - The listing check runs in the background, not in the calling request. A synchronous check
    put a LIST on every click a minute apart: warm was ~240 ms, only ×3.5. The card's "a
    rebuild never blocks queries on the current connection" allows a background check.
  - Combined-table cache: two in-memory copies of each cached table (parts and combined) in
    exchange for an 8× faster copy into DuckDB.
  - Residual case, documented: a file written *and* merged into an existing compacted file
    between two of the dashboard's listings leaves the key set unchanged. That partition then
    misses the late rows until another of its keys disappears or the process restarts. Keys-only
    listings (`StorageBackend.list`) cannot show it.
- Outside Owns: `tests/unit/app/test_tearsheet.py::test_shared_connection_is_reused_then_replaced_and_closed`
  expected a rebuild after 60 s with no store change, which the card removes. It now writes one
  file before moving the clock, asserts the old connection still serves while the check runs,
  and waits for the refresh. Every original assertion is unchanged.
